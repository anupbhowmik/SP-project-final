# Project Overview
This project simulates the memory usage of different Key-Value (KV) cache backends for large language model (LLM) inference. It focuses on how prompt prefix sharing can reduce memory waste. The simulation is multi-threaded and models how LLMs store and reuse token activations during sequence decoding.

## Anup Bhowmik
========== Simulation Setup ==========
Implemented a simple multi-threaded simulation for sequence decoding using a KV backend.
This simulator models the memory usage of LLM (Large Language Model) KV (Key-Value) caches during concurrent decoding.

------------------ Features ------------------
KV Cache: 
In transformer models, each token processed generates key and value vectors that are stored in a cache for use in future attention computations.

Multi-threaded Simulation:
Each sequence is processed in a separate thread using POSIX threads (pthread). Threads simulate prompt token generation.

Token Generation Simulation:
For each sequence, tokens are appended to the backend for both prompt and generation phases. Sleep (usleep) simulates processing time per token.
Other steps (like attention, feedforward, attention, softmax, or neural network layers, etc.) are not simulated because They do not affect the memory layout of the KV cache.
The simulator's goal is to measure peak memory usage for the cache, not to simulate the full computation of the model.

Thread Arguments Struct:
ThreadArgs struct passes necessary data (backend, config, work, index) to each thread.

Backend Interaction:
Uses functions from kv_backend.h to initialize sequences, append tokens, and collect statistics.

Resource Management:
Dynamically allocates and frees memory for thread handles and arguments.

Statistics Collection:
Returns backend statistics after all threads complete.


========== Main Setup ==========
contains the entry point and main simulation driver for the project. It sets up the simulation configuration, generates a workload with shared prefixes, runs two different KV backends (monolithic and paged with prefix sharing), and prints memory usage statistics for each backend.

Steps:
1. Setup mono KV backend and page KV backend and their configuration
2. Initialize random seed
3. Generate a workload array of SequenceWork structs, ensuring that sequences are grouped for shared prefix simulation. Each group here share the same prompt prefix
4. Run simulation (both mono and paged)
5. Print stats and results
6. Free workload and other allocations

## Tawheed Islam Bhuian
========== Page Allocation and KV Backend ==========
goal is to design LLM backend that allocates memory in fixed-size “pages” (token blocks) and optionally shares prefix pages across sequences, so physical allocation tracks usage more closely than “one fixed 2048-window buffer per sequence”.

Backend creation:
Steps:

1. create_paged_backend allocates KVBackend and PagedKVImpl, copies cfg, and initializes impl->mutex.
2. It creates a fixed-size page pool via page_allocator_create:
    a. Computes page size and number of pages.
    b. mmaps a single arena.
    c. Initializes Page metadata and populates the allocator free list.
3. Prefix-sharing groups (SharedPrefix) are allocated if enabled, but no pages are allocated yet.
4. The backend vtable is wired and returned. arena exists; all pages are free.

Sequence initialization:

Steps:

1. paged_init_sequence reserves a sequence slot.
2. Computes shareable prefix length (page-aligned).
3. If prefix sharing is enabled:
    a. Selects a group.
    b. Lazily builds the group prefix by allocating pages from the allocator.
    c. Attaches prefix pages to the sequence and increments page refcounts.

Token append:

Steps:

1. paged_append_token computes the target page index from the token count.
2. If the page slot is empty:
    a. Allocates a page via page_alloc (popped from free list, ref = 1).
    b. Tokens fill pages sequentially; allocation is lazy and page-granular.

Sequence finish:

Steps:

1. paged_finish_sequence decrements refcounts for all pages in the sequence.
2. Pages with ref == 0 are returned to the allocator free list.

## Evan Dreher
========== Monolithic KV Backend ==========
Implemented a simple monolithic KV cache backend that stores all KV cache data in contiguous memory buffers.

Structures:
1. MonoSeqState struct that tracks the state of a single sequence implementing a monolithic backend
    - max_tokens: number of tokens this sequence can have
    - cur_tokens: number of tokens this sequence already has
    - bytes_per_token: size of the KV data (size K + size V)
    - kv_buffer: buffer that holds all data for this sequence

2. MonoKVImpl structu that is an Implementation state for the monolithic KV backend
    - cfg: config params
    - seqs: all sequence states
    - num_seqs: current number of active sequences
    - capacity: current allocated capacity of the seqs array
    - mutex: mutex lock for sequence management

Operations:
1. Initialization (mono_init_sequence):
    - allocates a sequence slot
    - grows the sequence array dynamically if its at capacity
    - pre-allocates the KV buffer upfront

2. Token Append (mono_append_token):
    - increments the token counter if space is available, otherwise fail silently
    - In a real system, this would also write KV cache data to the buffer

3. Sequence Finish (mono_finish_sequence):
    - This is a no-op implementation; no deallocation occurs
    - In a real system, this could trigger memory reclamation or accounting updates

4. Statistics (mono_stats):
    - counts total tokens
    - counts total physical bytes allocated from buffers
    - counts amount of wasted memory

5. Cleanup (mono_destroy):
    - the deallocator function

========== Workload Generation ==========
Implemented the workload generator that creates synthetic LLM inference scenarios for testing the backends.

Features:

1. Shared Prefix Grouping:
    - all seq are split into groups by their common prompt prefix
    - this enables testing of prefix-sharing optimizations

2. Page-Aligned Prefixes:
    - base prefix length is set to 128 pages
    - aligned to tokens_per_page to allow us to efficiently reuse pages

3. Random Prompt Variation:
    - each sequence gets its shared prefix plus some randomly generated number of extra tokens.
    - models varied input lengths despite the shared prefix.

4. Random Generation Length:
    - each sequence generates a random number of tokens
    - models varied output lengths across concurrent requests

Output:
- one SequenceWork struct per sequence
- SequenceWork:
    - prompt_tokens: total prompt length
    - gen_tokens: number of tokens this sequence will generate
    - shared_prompt_tokens: number of tokens in the shared prefix
    - shared_prompt_id: group number
